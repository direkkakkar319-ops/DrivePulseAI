# DrivePulseAI: dataset audit and sourcing

**Frozen product domain: passenger cars and passenger EVs only (user decision, 2026-11-13). Heavy trucks, buses, aircraft and industrial datasets below are included only as out-of-domain references/benchmarks and must not support car performance claims.** Component X v3 was subsequently fully acquired and audited; it is not a car dataset.

Audit date: 2026-11-13. Local dataset counts and validation notes below are from `data/README.md` (audit narrative dated 2026-10-04) and the current raw tree. The raw contents were not modified or model-trained during this audit. The external source links below were checked through web search against dataset publisher/maintainer pages where available. “Unverified” means the local source/version/license could not be established or the external page did not specify a license. Dataset licensing can differ between the host’s metadata and upstream source terms; cite and follow the source distribution’s own terms.

### Historic code findings and warnings

`ml/src/data/loaders.py` currently contains loaders for Scania APS, KIT and carOBD. Older `data/README.md` statements that no KIT/APS loaders existed are stale. The same audit notes older AI4I/C-MAPSS mappings and whole-input scaling risks; treat these as warnings about historical experiments, not a claim that current APS training uses those mappings. Current APS training path uses `load_aps`, train-fitted imputation and official test split (`ml/src/training/train_failure.py`). The current failure classifier does not chain upstream model outputs.

## Part B — should the project change datasets?

1. **Anomaly Detection: KEEP KIT for a limited car-only exploratory baseline; otherwise change/qualify.** KIT records are passenger-car OBD telemetry but have no mechanical anomaly labels. Review Nissan Leaf data from PR #50 only after verifying its source/license. Exclude Component X because it is truck data. Keep carOBD out of validated claims until its provenance and schema defects are resolved. Do not treat CAN cyberattacks as mechanical faults.
2. **RUL / Health Score: CHANGE.** No verified passenger-car/EV RUL dataset is currently in the repo. Component X v3 has valid time-to-event structure but is heavy-truck data, so it cannot support this car-only project’s model claims. Acquire a passenger-car/EV battery or vehicle maintenance dataset with documented unit-level degradation and event labels before training.
3. **Failure Classification: CHANGE for passenger-car claims.** Scania APS and Component X labels are truck-only. KIT/carOBD lack verified future mechanical failure labels. A passenger-car/EV failure source must specify observed subsystem events, prediction horizon and censoring/negative follow-up; do not use AI4I as automotive evidence.

**Combined verdict:** no consistent passenger-car/EV dataset story supports the entire chain yet. Component X v3 is well-formed for a separate truck-component study but explicitly out of scope here. KIT can support only car telemetry novelty exploration; Scania APS cannot support car classification. These datasets must remain separate and must not be joined into a car performance claim.

## Step 2 strategy decision pending

The gate requires a user decision before any new download. Options are:

1. **Unified passenger-EV source:** preferred if a source supplies battery telemetry, independent degradation/health targets and dated failure outcomes for the same vehicles. None currently verified in this repository.
2. **Per-stage passenger-car/EV sources with an explicit interface:** use KIT only for unsupervised anomaly exploration, a rights-cleared EV capacity/SOH source for health forecasting, and a separately verified vehicle-level failure source. This supports separate benchmarks and software handoff tests, but cannot support one empirical chained performance claim across different assets.
3. **Surrogate source:** use Component X or C-MAPSS for method debugging only. This is not acceptable evidence for passenger-car performance.

**Recommended strategy:** choose option 2 while continuing to search for a unified source. Do not download another large or restricted dataset until you confirm this strategy. The first product claim should be passenger-EV battery anomaly/capacity health, with RUL and forward failure classification explicitly deferred until independent event labels and rights are available.

| **HCRL Car-Hacking** — [HCRL page](https://ocslab.hksecurity.net/Datasets) | Millions of CAN frames with normal vs injected cyberattack classes; automotive network security, not physical failure. **Scarcity statement:** open real automotive datasets with vehicle identity, time-aligned component maintenance/failure outcomes and RUL/TTE are scarce. OBD/CAN streams commonly lack mechanical labels; service histories commonly lack high-frequency telemetry. Dataset naming alone does not bridge this gap.

## Part D — recommended dataset strategy

### Recommendation

Keep the initial product claim narrow: **passenger-car/EV battery health**, with a car OBD anomaly baseline as a separate exploratory task. The 20-car on-road EV capacity dataset (BAIC EU500) is acquired and schema-audited, but its repository license does not explicitly cover the data, so it remains blocked from model work pending data-specific permission. The 347-EV Figshare data is acquired under CC BY 4.0. Its paper does not confirm passenger-car body type and reports 347 / 55 abnormal / 292 normal while local label files contain 348 / 55 / 293. Labels are vehicle-level without verified event time; complete joins and cutoff semantics remain unchecked. Neither source is approved for model work until its respective gates pass. Do not claim an end-to-end chain until units, cutoffs, targets and signals are proven aligned. Component X v3 and Scania APS are truck-only and excluded from car results.

The acquired 20-car data remains quarantined from model work pending data-specific rights. If permission is obtained, an honest first experiment is **future capacity/SOH prediction**, not RUL: the supplied capacity target is computed from current and SOC over a charge window, and there is no independent end-of-life event or official split. A past-to-future, held-out-vehicle trajectory evaluation is possible, but report target construction and the estimated nature of capacity explicitly. True RUL requires an independently defensible EOL threshold/event and observations that support time-to-crossing evaluation. Do not infer failure labels from a predicted health score.

### Bridging schema and leakage rules

1. Keep each source’s raw fields and source IDs; build an explicit mapping table from native field → canonical field → unit → availability → component → evidence. Missing mappings stay unmapped; never rename torque/tool wear/anonymous engine sensors as car signals.
2. Canonical observations: `source_id`, `dataset_version`, `asset_id`, `component_id`, `timestamp`, `signal_name`, `value`, `unit`, `quality_flag`; preserve data lineage and time zone/clock precision.
3. Canonical sample: component window `[start,end]`, feature schema version, per-signal coverage/missingness, and only as-of-time measurements. Attach anomaly output and model version, then RUL/TTE estimate and uncertainty, then event-risk output/horizon.
4. Split by asset/vehicle first, preserve official split, and use temporal cutoff within training assets. Fit scaling/imputation/feature selection only on train; generate upstream predictions out of fold for downstream model training. Do not let overlapping windows cross partitions.
5. Failure label: `1` only if independently recorded component failure occurs within horizon H after cutoff; `0` only if observable follow-up covers H without failure; otherwise censored/unknown and excluded or handled by survival methods. Never define ground truth by the same health-score threshold that is a Stage 3 feature.
6. Report each domain separately. Say “Scania truck component benchmark,” “Seat Leon OBD anomaly exploration,” “synthetic software fixture,” or “NASA aircraft benchmark” accurately. Do not claim passenger-car RUL from Scania or NASA results.

### Next-session acquisition and preprocessing checklist

1. For passenger-car/EV work, verify dataset terms, target semantics, vehicle identity, files and splits. The 20-car capacity archive data rights remain unresolved. The 347-EV release is acquired, but passenger-car status, the 347/348 count discrepancy, exhaustive joins and event horizon remain unresolved. Component X v3 is truck-only and excluded.
2. Decide whether large raw files belong in Git, Git LFS, or external documented storage before download. Do not store secrets/credentials or use unreviewed mirrors.
3. Download source archive/files to a staging directory; record byte size, SHA-256, headers, row counts, encoding, missingness, IDs, time ranges, and per-file schema. Preserve original files unchanged.
4. Read the source paper/data dictionary and document each target’s construction, measurement units, sample timing, censoring/event meaning, privacy and official split semantics.
5. Validate asset/vehicle IDs and time alignment across files; quantify unmatched IDs, per-asset coverage and target availability. Do not invent failure labels or infer EOL from predicted health.
6. Create a non-mutating inventory and schema report; do not preprocess until joins/target semantics are reviewed.
7. Define train/validation/test by asset identity and time using the official split; explicitly test no asset leakage and no window overlap.
8. Only then implement separate loaders and baseline experiments, with train-only transforms, seed/config manifest, simple metrics and limitations.
9. Keep KIT/Leaf anomaly data and any truck benchmark in separate manifests and result tables. The end-to-end contract demo may use a clearly watermarked synthetic fixture until real passenger-car labels support a full chain.

## Step 2 — passenger-car/EV replacement audit

**Status: 🟡 Partial; strategy confirmed, one health/SOH source acquired, failure source acquisition blocked, and no valid car RUL/TTE source found.**

### Tongji real-world EV SOH release

- Source/version/license: Zenodo record 16868546, DOI `10.5281/zenodo.16868546`, CC BY 4.0. Raw archive is unchanged at `data/automotive_prognostics/tongji_rest/v1/raw/data.zip`; provenance and checksums are in that folder's README.
- Reproducible audit: `./.venv/bin/python ml/scripts/audit_tongji_rest.py`; output `ml/reports/data_validation/step2_tongji_rest.json`.
- Audit result: 154 XLSX files, 26,450 data rows, 148 train files and 6 test files. The files expose fast/slow feature families with 123–184 columns and fields such as `t_start`, `t_end`, `mileage`, SOC, voltage, capacity, `soh`, internal-resistance/voltage statistics and battery feature summaries. The archive contains 78 `car_identifier` values.
- Split/leakage result: the nominal train/test directories are not independent-vehicle splits. `GE16` and `HQ05` occur in both; only `P215` is test-only. The audit also counted 39 backward `t_start` steps (30 train-fast, 9 train-slow). These must be removed from any claimed held-out evaluation.
- Target verdict: `soh` and capacity are measured/derived health proxies, not a documented run-to-end-of-life event. No future-failure horizon, censoring rule, or mechanical component label is present. **Anomaly: 🟡 partial for battery-signal novelty; RUL: ❌ invalid as observed RUL; health/SOH regression: 🟡 usable only after a vehicle-disjoint split; failure: ❌ invalid.**

### Shenzhen EV charging-fault release

The metadata confirms CC BY 4.0, release v3, two XLSX files, 21,175 charging sequences, 1,547,432 one-minute samples, 10,154 EVs, and `label=1` faulty battery / `0` normal.
- The release is a contemporaneous battery-fault classification source, not a documented future failure-within-horizon or RUL source. Passenger-car status is supported by the Astrolabe registry but is not explicit in the primary Mendeley description; this remains a caveat until file-level inspection.

The recommended multi-source strategy is accepted for separate benchmarks: KIT remains an unsupervised OBD novelty benchmark; Tongji is a candidate SOH/health regression benchmark; Shenzhen is a candidate battery-fault benchmark once the official asset can be fetched.
